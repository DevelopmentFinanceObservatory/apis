# Datasets API (V1) conformance matrix

This document tracks how the datasets materialisation implementation conforms to the Datasets API contract (V1), clause by clause. Last verified against the code and issue tracker: 2026-09-16.

Status values:

- **implemented** — verified against the code; behavior matches the clause.
- **partial** — some but not all of the clause is met.
- **missing** — no implementation exists for this requirement.
- **divergent** — an implementation exists but behaves materially differently than the clause specifies.
- **n/a** — out of scope for this contract at V1 (deployment policy, or explicitly excluded).

Gap rows state what is needed to close the clause and name the open issue that tracks it (**none** when no open issue exists). Gaps spanning several clauses are grouped by root cause in "Open gaps" at the end.

### Routes that postdate the V1 contract

Five routes are outside the V1 contract text. The code registry's mappings for `datasets.publish`, `datasets.recipe`, and `datasets.refresh` are the normative source for their refusal codes, `src/datasets_api/README.md` describes their behaviour, and `tests/live_refresh/wire_pairs.json` records a request and response for each. Every one checks the caller named in the `DATASETS_PRINCIPAL_HEADER` header before it validates the path or reads the body.

| Route                                                         | Caller                           | Answers                                                                                                                                                                                                                                                                              |
| ------------------------------------------------------------- | -------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| POST /api/datasets/frames/publish                             | `DATASETS_FIRST_PARTY_PRINCIPAL` | Stores a derived frame (`ops_` id, `ocv_` version) and, when the body carries `recipe`, its recipe. 200 `{schema_version, published: {spec_id, content_version, artifact_digest, created}}`                                                                                          |
| PUT /api/datasets/frames/{spec_id}/{content_version}/recipe   | `DATASETS_FIRST_PARTY_PRINCIPAL` | Stores the recipe of a published derived frame. 200 `{spec_id, content_version, created}`. A pair keeps its first recipe; a different `normal_form_hash` or `replay_key`, or a `replay_key` another frame holds, refuses `publish_conflict` (409) with the cause in `constraint_id` |
| GET /api/datasets/frames/{spec_id}/{content_version}/recipe   | `DATASETS_FIRST_PARTY_PRINCIPAL` | 200 the stored recipe as first written, or `recipe_not_found` (404)                                                                                                                                                                                                                  |
| GET /api/datasets/recipes/replays/{replay_key}                | `DATASETS_FIRST_PARTY_PRINCIPAL` | 200 `{spec_id, content_version}` of the one frame whose recipe carries the key, or `recipe_not_found` (404)                                                                                                                                                                          |
