# Search API (V1) conformance matrix

This document tracks how the search engine implementation conforms to the Search API contract (V1), clause by clause. Last verified against the code and issue tracker: 2026-08-08.

Status values:

- **implemented** — verified against the code; behavior matches the clause.
- **partial** — some but not all of the clause is met.
- **missing** — no implementation exists for this requirement.
- **divergent** — an implementation exists but behaves materially differently than the clause specifies.
- **n/a** — out of scope for this contract at V1 (deployment policy, or explicitly excluded).

Gap rows state what is needed to close the clause and name the open issue that tracks it (**none** when no open issue exists). Gaps spanning several clauses are grouped by root cause in "Open gaps" at the end.

| C12    | parsed carries parts (list of variable_text/entities/time_text/unit_text/source_text/operations) plus optional raw_query, all capped and validated; each part's operations are echoed onto the part it resolves. Every request part (a parsed part and each dataset_resubmit entry) carries at most 8 operations, at least the 8 extract keeps per query (`extract.MAX_OPERATIONS`), so a part the engine echoes always posts back. A posted operation phrase is caller-authored and reaches the bind prompt as one list line, so `Operation.phrase` is capped at 200 characters, the longest phrase extract echoes, and a blank phrase or one holding a newline, a Unicode line or paragraph separator (U+2028, U+2029) or another control character refuses with a validation error. An extracted phrase must have its words in the query in order and pass the same model as written, or extract discards the operation; a phrase over 200 characters is discarded whole, since a cut phrase still reads in order and asks for less than the query did. Phrase and query are compared NFKC-normalised and casefolded, so halfwidth katakana and fullwidth Latin and digits match their ordinary forms, and each space-separated piece of a phrase is matched on its own. A piece holding a character of a script written without word spaces (CJK and its iteration mark, Hiragana, Katakana, Thai, Lao, Khmer, Myanmar, Tibetan) has no word edges, so it must occur in the query as an exact substring, in order: "上位5ドナー" in "教育援助の上位5ドナー" and "最大的五个捐助国" in "教育援助最大的五个捐助国是哪些" are admitted, "最大的十个捐助国" in the latter is not. A Latin or digit piece, and the Latin or digit end of a mixed piece, matches only where the neighbouring query character is absent, is no letter or digit, or belongs to one of those scripts: "TOP5" in "教育援助額TOP5" and "top 5" in "教育援助のtop 5ドナー" are admitted, "top 5 ドナー" in "教育援助の top 50 ドナー" and "上位5" in "教育援助の上位50ドナー" are not. A digit end also refuses a group or decimal separator followed by a digit, so "top 10" in "top 10,000 donors" and "top 2" in "top 2.5 percent" are not admitted. Hangul is written with spaces, so a Korean piece matches whole words only. `Operation.target_year`, a year from 1000 to 2200 (`MAX_FORECAST_TARGET_YEAR`), is the year a forecast projects to; it refuses on any other verb, rides with the part through every door and restatement, and does not affect resolution. The model reads no clock, so a posted value within the bound is taken as given and a stored part posts back in any later year; the raw_text door alone holds it to a year after the current one | implemented |                                                                                                                                        |
