# Datasets API

The Datasets API registers, mints, materialises, snapshots, and pins dataset specifications for the Development Finance Observatory (DFO). It resolves statistical variable definitions against Data Commons and SDMX endpoints, executes synchronous tabular materialisation, generates Frictionless data packages, and persists rendered artifacts to Google Cloud Storage and PostgreSQL.

The surface mounts on the shared FastAPI platform at `/api/datasets`.

---

## Architecture and Doors

The surface composes six functional doors into a unified router, error classifier, and lifespan context.

```
/api/datasets
├── /healthz                             (Meta door)
├── /schema                              (Meta door)
├── /capabilities                        (Meta door)
├── /operations/{operation_id}           (Meta door)
├── /register                            (Register door)
├── /                                    (Mint door)
├── /{id}                                (Definition door)
├── /{id}/{content_version}              (Snapshot door)
├── /{id}/versions                       (Versions door)
├── /{id}/{content_version}/files/{digest} (Files door)
├── /{id}/{content_version}/file         (Files door)
└── /{id}/{content_version}/pin          (Pin door)
```

### 1. Meta Door

Handles service liveness, capability negotiation, and schema discovery.

| Method | Endpoint                           | Description                                                                                                            |
| :----- | :--------------------------------- | :--------------------------------------------------------------------------------------------------------------------- |
| `GET`  | `/api/datasets/healthz`            | Returns liveness status, the running build commit, and the capability version (`{status, build, capability_version}`). |
| `GET`  | `/api/datasets/schema`             | Returns contract-stable JSON Schema definitions for dataset models.                                                    |
| `GET`  | `/api/datasets/capabilities`       | Returns runtime capabilities, format options, and the sync budget.                                                     |
| `GET`  | `/api/datasets/operations/{op_id}` | Polls asynchronous operation state (`operation_not_found`, 404, for an unknown id).                                    |

Every response carries `x-dfo-commit`, and every response that is not shared-cacheable (`Cache-Control: public`) also carries `x-dfo-trace-id` and `Server-Timing`. Healthz carries all three. `/schema` and `/capabilities` are shared-cacheable and carry `x-dfo-commit` alone. `build` in the healthz and capabilities bodies equals the commit `x-dfo-commit` carries.

A request refused because an executor, permit or operations backlog is full answers `service_unavailable` (503, retryable) with `Retry-After: 1`, the same value across doors (`dfo_platform.problem.BACKPRESSURE_HEADERS`, which the Graph surface's saturation 503 sends too); a new pin over `DATASETS_PIN_DAILY_MAX` or `DATASETS_PIN_OPEN_DAILY_MAX` answers the same code and `retryable: true`, with `Retry-After` counting the seconds to the next UTC midnight, when the budgets reset.

### 2. Register Door

Registers canonical dataset specifications directly in the registry.

| Method | Endpoint                 | Description                                    |
| :----- | :----------------------- | :--------------------------------------------- |
| `POST` | `/api/datasets/register` | Persists a canonical specification definition. |

Each definition's `identity` field holds a document shaped as `search.models.identity.BaseIdentity`, published at `GET /api/search/schema`.

### 3. Mint Door

Resolves input variables, registers definitions, materialises observation data synchronously, and writes artifacts to storage.

| Method | Endpoint        | Description                                     |
| :----- | :-------------- | :---------------------------------------------- |
| `POST` | `/api/datasets` | Mints and materialises a dataset specification. |

Supported payload request types:

- `statvar_set`: One StatVar, in `statvars`, which holds exactly one `dcid:`-prefixed entry.
- `spec_id`: Existing canonical specification identifier.

A posted `preview` field refuses `request_invalid`. Every route that takes `{id}` accepts `spec_` ids only, and a `col_` id answers 404 `not_found`.

A mint sent with the header `X-DFO-Mint-Admission: background` warms data no caller waits on yet (`datasets_api.background_admission`). It is admitted only without waiting and only while it leaves a place for foreground callers. It takes its work slot and materialise permit only while at least one of each stays free after it. It does not wait for a rebuild of the subject another caller is running. Over the sync budget, it records a new operation only while one backlog place stays free after it. Where any of these fails, or the graph release it bound has been replaced, it answers 503 `service_unavailable` with `constraint_id` `mint_background_declined` and queues nothing. Once admitted it runs as a foreground mint does, including the wait of up to its deadline for the groupby fold permit, so a fetched frame is not discarded. A head that already links the requested rendering answers it as it answers any mint. The operation it submits runs on the worker as any other. Any other header value, or none, admits the mint as a foreground mint.

A `range` window on a role-bearing StatVar, one that declares a role besides `observationAbout`, is held to the rule Search's role routes read years by (`search.scope_window.role_read_years`). Its years start no earlier than `SEARCH_SCOPE_MIN_YEAR` (1960) and the coverage index's first year, end no later than the coverage horizon's last year, and number at most `SEARCH_SCOPE_MAX_WINDOW_YEARS` (80). A longer window refuses `request_invalid` (400) before any registry write, with the pointer `/input/scope/window`, or the posted definition's `/identity/requested_window` when a sidecar's own window is at fault, and a message such as "A window reads at most 80 years of data; 1900 to 2060 reads 1960 to 2060, which is 101 years." or, for a window no floor or horizon moves, "A window reads at most 80 years of data; 1960 to 2060 is 101 years." The `/options` and `/members` routes admit a posted definition by the same rule. A window the mint serves therefore resolves when Search resubmits the minted identity. A subject-only StatVar reads every year its window names.

An entity a role-bearing mint binds under a flow role, by `scope.entities` or the posted definition's `identity.entities`, must be of a kind the role takes (`search.role_kinds`, the rule Search's resubmit refuses by). A role takes the kinds of the parties the code index lists on its flow axis: a country, an organisation and an aggregate on both, a group of countries where a total holds one, and on the recipient side the continents and subregions a regional total holds. Another entity refuses `invalid_role_ref` (422) before any registry write, at `/input/scope/entities/<role>`, the posted definition's `/identity/entities/<role>`, or `/input/spec_id` for a registered identity's own entity, with a message such as "Count_Person is a statistical variable; a recipient is a country, an organisation, a group of countries, a continent, a subregion, or an aggregate of other parties." An entity neither the graph nor the membership policy holds refuses the same way. A role whose axis the index lists no party on is not checked, since no kind can be derived for it. The `/options` route checks a posted definition it registers; `/members` registers nothing and does not.

### 4. Definition Door

Re-runs materialisation on demand for an existing registered identifier using the latest available upstream data.

| Method | Endpoint                     | Description                                                                                                            |
| :----- | :--------------------------- | :--------------------------------------------------------------------------------------------------------------------- |
| `GET`  | `/api/datasets/{id}`         | Re-materialises observation data for a `spec_` identifier.                                                             |
| `GET`  | `/api/datasets/{id}/options` | Returns the `OptionsEnvelope` (output options, coverage, `content_version`) without rendering.                         |
| `POST` | `/api/datasets/{id}/options` | The same envelope for a spec whose canonical `definition` the body carries, registered or not.                         |
| `POST` | `/api/datasets/{id}/members` | The members a mint of a `spec_` id serves, with their labels and the family's count and digest, without materialising. |

Query parameters:

- `format`: Target output serialization (`csv`, `xlsx`, `parquet`).
- `bundle`: Frictionless Data Package bundling boolean (`true`, `false`). A bundle is a zip of `README.md`, `data/<slug>.<ext>`, `data/codes.csv` (when the data holds codes), `SOURCES.md`, `CITATION.cff` and `datapackage.json`, built by `materialise.bundle.assemble_bundle`. A long CSV bundle whose definition leaves a flow role open, or binds it to several entities, writes the rows where that role holds a total (`<role>_kind` is `total` or `whole total`) to a second data file, `data/<slug>-totals.csv`, and its README says where they are, or that the main file is empty when every row is a total. A download is named `dfo_<sources-slug>_<YYYY-MM-DD>_<format>_<cv6>.zip` (`artifact_delivery.artifact_file_name`), and a bare file `dfo_<sources-slug>_<YYYY-MM-DD>_<cv6>.<ext>`. A rendering that reshapes the long table (`pivot`, `groupby`, `columns`, `layout: "frame"`, or an incomplete rendering) adds a shape token such as `pivot-9c1fe3` before `<cv6>`, after `<format>` in a zip name (`render._file_shape`), so two renderings of one version under one extension take two names.
- `groupby.by` / `groupby.op`: The axes a sum keeps (comma-separated) and its operation (`sum`). Every other declared-summable axis the frame decoded, and `stat_var`, is summed away. When every decoded axis the sum leaves alone holds one value, the result is a grammar frame with its own `content_version`: `stat_var` is `dcid:<spec_id>` on every row and each kept code axis is a `stat_var_<code_system>` column of labels.
- `groupby.levels`: Comma-separated `<code_system>:<depth>` pairs, such as `crsPurpose:0`. Each kept code rolls up to its ancestor at that depth before the sum (0 is the root codes), so `groupby.by=time_period,crsPurpose&groupby.op=sum&groupby.levels=crsPurpose:0` gives one row per year, donor, and recipient for each of the ten CRS sector groups. A code above the depth stays as itself, its row carrying its own label; depth 0 leaves none. `GET /api/datasets/capabilities` lists the axes it accepts as `groupby_level_axes`.
- `pivot.index` / `pivot.columns`: Dimension pivoting configuration.
- `columns`: Comma-separated column projection selection. A list that names only enrichment columns keeps every default column and adds them; a list with any table column selects. Unpivoted output keeps every decoded `stat_var_<code_system>` column unless the list names some. The long layout ignores `status` and `<role>_label` (written by default; the options document still offers `<role>_label` because pivot output writes names only on request); the frame layout keeps `status`. The long layout is fixed: `stat_var` (with `stat_var_label` when no code system decodes), each entity with its `_label`, its `_kind` for a role on a flow axis, and its enrichments, each code system as `<code_system>` (the code) and `<code_system>_label`, then `time_period` (an integer when every period of the frame is a year point, otherwise text in every row), `value`, `unit`, `unit_label`, `currency`, `price_basis`, `base_year`, `measurementMethod`, `measurementMethod_label`, `provenance` and `provenance_label`. An empty build types `value` as a number, as a build with rows does, but `time_period` and `base_year` take their type from the data, so an empty file writes them as strings. A name the graph lacks or a failed name read leaves its cell empty with an `enrichment_unavailable` warning. Three party fields come from the code index with no graph read (`CodeIndex.parties`, which carries the reviewed overrides, such as the World Bank Group as a total of its institutions): `party_kind` is the party's kind (`party`, `total` or `residual`), `party_class` its class (`official`, `private` or `residual`, for a total the one class its whole markers cover, empty when they cover none or several), and `party_whole` is `true` on a row whose party is a total that holds every party of its classes on its axis in that row's dataset and year (`PartyRow.whole`), such as Official Donors, Total, and `false` on a row where it is not. It is empty for a party with whole markers where the row names no one dataset and year: a row with no `provenance`, one whose `time_period` spans years where the marker sets a window, and every pivot, which reads party cells for no dataset and year. The long layout writes one `<role>_kind` column for every role on a flow axis whatever the data holds, so every version of a dataset has the same columns, and reads it from the three in words: a party on the provider or creditor side reads `official` or `private`, one on the recipient or debtor side `country or organisation` (`private` for a private party), a total `whole total` where its `party_whole` is `true` and `total` elsewhere, and a residual `unallocated`. The options document lists the enrichment columns the long layout writes by default as `long_layout_defaults`; naming one gives that column once, and the long layout ignores party field tokens. Pivot output and the frame layout write a party field only when a token asks for it, as `<role>_party_kind`, `<role>_party_class` or `<role>_party_whole`. Each belongs to party roles only (roles on a flow axis). A bare `party_kind`, `party_class` or `party_whole` requests it for every party role the table has, so a caller asks for kinds without knowing which roles the table carries; a qualified token naming a role the table lacks, or a subject role such as `observationAbout`, refuses `column_unknown`, and the options document offers no party field pair for a subject column. It lists `party_class` and `party_whole` for each party role with the coverage of its `party_kind`, since one index row fills all three. Every path reads the party cells the same way, from the code index with no graph read, so the split of totals holds whatever the graph's health. A party the index does not list gets empty cells and an `enrichment_unavailable` warning, stays in the main table, and counts as uncovered in the options document's `party_kind` coverage. A long CSV or XLSX keeps total rows out of its main table, since a sum over a role that counts a total counts its members twice. A row is a total when a role listed in the options document's `long_layout_totals` holds a party of kind `total`, whole or not; the render and the options document read one rule (`output_options.movable_totals_roles`). A role bound to one entity makes no total row ("ODA from the UK to developing countries, total" keeps every row), and residuals stay with the parties. A bundle's CSV writes the totals as a second data file and an XLSX on a second sheet `totals`; an XLSX whose data sheet holds no row takes its Data Package schema from the totals sheet. A bare CSV has no README and drops them, so the options document's `long_layout_totals` is where a caller learns of the drop. It names only the roles where a total row can exist: a role bound to several entities one of which the code index declares a total, and an open role when the index lists a total on its axis in a dataset the definition read (any dataset, when the read selected none). Recipients bound to Kenya and Ghana are not listed. Parquet, pivot output and the frame layout keep every row. A column that is not droppable refuses the request with `column_not_droppable`; `GET /api/datasets/{id}/options` reports each column's `droppable` flag before a caller corrects the list by trial.
- `layout`: `frame` writes a bare Parquet file in the frame layout instead of the long layout: the frame's columns as reshaped, with each decoded code system as `stat_var_<code_system>` (its label), `status` kept, a converted unit as the frame grammar's JCS text of the unit request, and no name columns or name reads (`render.FRAME_LAYOUT`). It is the layout machine readers such as data-mcp request; the long layout is the download default. The artifact's `rendering` carries `layout: "frame"` as sent and no layout version, and the snapshot lists it after the long-layout files. `layout` with `bundle=true`, a pivot, or a format other than `parquet` refuses `request_invalid` at `/options/layout`.
- `without_party_totals`: `true` leaves out group totals. Flow datasets such as OECD DAC2A list totals (the DAC total, the G7, DAC EU members) as parties beside their members. For each flow party role the served identity binds no entity on, the rows whose party the code index declares a `total` (`CodeIndex.parties`, whole totals included) leave the frame; parties, residuals and parties with no declared kind stay, a role on which every row is a total keeps them, and a role the identity binds keeps every party. The cut runs on the frame before any other reshape, so a `groupby` sums the members it kept. Like a `groupby` collapse, a cut that leaves rows out mints a version of its own, hashed over the cut frame and recorded with `base_content_version`, its own canonical frame, statistics, output options and description, and every file of it renders the cut frame. Its manifest's `trace.party_totals_left_out` lists `{role, provenance, entities}` for each role and provenance that lost rows, `provenance` null for rows with none, so a party left out of one dataset is named for that dataset alone. A version recorded before the trace named the provenance lists `{role, entities}`, whose parties left the rows of every dataset. A cut that leaves nothing out serves the frame's own version. A `groupby` with the option mints one version over the sum of the cut frame, and its file records both options, which a frame refresh mints again. The rendering records the option only when true (`render.artifact_rendering`).

The mint body also takes `options.enrichment: "default"`, which asks for the version's default enrichment columns once it is built (`default_enrichment`): the `_type` column of each of `observationAbout`, `financingProvider` and `financingRecipient` the frame holds, and `party_kind`, `party_class` and `party_whole` when it holds a flow party role. They join `columns`, or are the columns when it names none, and the answer, its `rendering.columns` and its stored file are those of a mint naming the resolved columns. The query namespace has no `enrichment` key.

`POST /api/datasets/{id}/options` takes `{"schema_version": 1, "definition": {...}}`, the `definition` a search response carries for the spec, so a caller can read the formats, columns, and enrichments of a search result before anyone mints it. The identity must hash to `{id}` and `definition.spec_id` must name it, or the call refuses `spec_id_mismatch`. A registered id answers as the GET route does. An unregistered definition is admitted as a `spec_id` mint admits its sidecar (`datasets_api.kinds.spec_id.admit_sidecar`), registered, and served as a registered id is. The rebuild records the version, stores the artifacts and advances the head, so the mint that follows is a head hit. A refusal from admission leaves no registry row. A refusal from materialisation after registration, such as `over_ceiling` or `facet_not_available`, leaves the row, as a mint's does. The call materialises the frame, holding the shared materialise slot as a mint does, and refuses `over_ceiling` above the inline ceiling, so a caller should send it when a visitor opens a download menu and keep default options until it answers.

`POST /api/datasets/{id}/members` takes a `spec_` id and an optional body `{"schema_version": 1, "definition": {...}}`, and answers `MembersEnvelope`: each member a mint of the spec serves, sorted by `ref` (`dcid:`-prefixed, as `trace.resolved_stat_vars` names it), with its graph `label` from one batched name read, its declared `roles` and its `constraints`; `served_count`; and `family_member_count` and `family_member_digest`, equal to the `trace` fields a mint of the spec states. A registered id needs no body. An unregistered one needs the `definition`, admitted as a `spec_id` mint admits its sidecar, and nothing is written. The route runs member resolution alone, so it costs no SDMX read, and it refuses as a mint's member resolution does: `spec_not_found`, `spec_id_mismatch`, `member_not_resolvable`, `spec_not_exportable`, `role_signature_incompatible`, `definition_not_reproducible`, `facet_not_available`, `over_ceiling` (`member_cardinality` or `candidate_window`). Query keys refuse `request_invalid`.

Members are a function of the identity, the graph and the release's code index. No request names one. A pinned identity serves its StatVar, and the code index decides the families it holds rows for. Any other described identity walks the graph's value-filtered reverse page of 4,000 subjects (`definition_candidate_cap`). A page that truncates without a confirmed root sends the walk to the whole filtered set, up to `DATASETS_MEMBER_SUBJECT_CEILING` subjects (`definition_subject_ceiling`), each confirmed by its arcs, so a family whose root sorts past the first page still settles and states its digest. A set above that ceiling refuses `over_ceiling` with `ceiling_kind: candidate_window`, and a walk whose reads run past `DATASETS_MEMBER_READ_SECONDS` answers `timeout` (504, retryable). The mint, definition retrieval, options and members routes and the operations worker share one process-level cache of resolved families, keyed on the graph generation (`statvar_members.shared_enumerator`).

### 5. Snapshot and Files Doors

Returns immutable version metadata and a stable download link for each stored artifact. Listing signs nothing.

| Method | Endpoint                                              | Description                                                                             |
| :----- | :---------------------------------------------------- | :-------------------------------------------------------------------------------------- |
| `GET`  | `/api/datasets/{id}/{content_version}`                | Retrieves stored artifact metadata and download links for a version.                    |
| `GET`  | `/api/datasets/{id}/{content_version}/files/{digest}` | Resolves one artifact's download link to a 302 at a short-lived signed URL.             |
| `GET`  | `/api/datasets/{id}/{content_version}/file`           | Redirects to the version's file in the `format`, `bundle` and `layout` the query names. |
| `GET`  | `/api/datasets/{id}/versions`                         | Lists a dataset's stored versions, newest first, one page at a time.                    |

A snapshot lists the version's canonical frame among its artifacts, rendering `{"format": "frame"}` and media type `application/vnd.apache.parquet`, after the requested files and before the statistics file, and downloads it as `dfo_<sources-slug>_<YYYY-MM-DD>_frame_<cv6>.parquet`. A frame1 document is never listed.

An artifact entry whose file holds party cells (`{role}_kind`, or a requested party field) read under the serving code index carries `enrichment_stamp`, that index's `CodeIndex.enrichment_digest`. The file is a long-layout file, or one whose `columns` name a party field, of a frame with a party role. The stamp salts the file's link key, so a code index export that changes a party's kind, class or whole marker re-renders it on the next request; a file of a frame with no party role has one link under every digest. A listed file rendered under an earlier digest with no current twin, such as a pinned file or an older layout, carries no stamp. A caller that names a frame by a file's rendering adds the file's own stamp to the name.

Every manifest names each artifact's `url` as `/api/datasets/{id}/{content_version}/files/{artifact_digest}`, relative to the API host, as the operation poll link is. The link never expires. A path id that is a posted, non-canonical spec id resolves through the bindings the registry stores (`datasets.spec_alias`): serving a posted id binds it to its served id, the canonical form of its identity under the code index, and the snapshot, files, pin and observations routes read a version under each served id bound to the path id, newest first, then under the path id itself. A code index export that changes the canonical form adds a binding and leaves the earlier ones, so a link issued under a posted id keeps resolving. A quarantined path id, or a quarantined served id bound to it, refuses `identity_quarantined`, on these routes and on every door that reads the definition (the definition GET, `/options`, `/members`, refresh and the mint): the registry read applies the rule (`spec_registry.reader`). A request to the link reads the version, its revocation and its base version's, and its link to the digest in one `dataset_store.snapshot.read_servable_version` transaction: a revoked version refuses `snapshot_revoked` (410) and signs nothing, an unknown version refuses `snapshot_not_found`, and an unlinked digest refuses `artifact_not_found`. A servable location is signed in hand for five minutes (`DOWNLOAD_SIGNED_URL_TTL`) and answered `302` with no-store headers. A working location past retention, in a rendering this build still renders (`render.rendering_options`), renders the artifact again from the version's stored frame on the work executor, under a materialise permit. The render renews the object under a new name. An incomplete rendering renders again as the complete rendering its request named, and its link resolves when that render yields the same bytes. When the frame has aged out too, the rendering is the stored frame (canonical or frame1), statistics or a superseded bundle or layout, or the render yields other bytes, the link refuses `artifact_expired` (410). The read and the signing run on the read executor. Presentation reads frames in process and never calls the route.

`GET /{id}/{content_version}/file?format=&bundle=&layout=` answers 302 at a signed URL for one file of the version in the requested rendering, with no principal check. The query takes those three keys alone, parsed as the definition GET parses them; any other or repeated key, or a value `MintOptions` refuses, answers `request_invalid` (400). The rendering is the version's recorded minting options with the requested format, bundle and layout laid over them, so a derived version renders as itself. A file of that rendering past retention whose bytes survive is renewed, as its link would renew it. Otherwise the rendering is rendered from the stored frame by `render_version_from_frame`, the function file renewal also calls, and an aged frame is renewed first. The selector refuses `artifact_expired` (410) only when neither the file's bytes nor the frame's survive.

`GET /{id}/versions?limit=&cursor=` is open to every caller and lists a dataset's stored versions, newest first, each with its `rendering`: `plain` for a raw version, `groupby` with the `groupby` a collapse was summed by, `without_party_totals` for a party-totals cut that sums nothing, and `not_recorded` for a derived version with no linked file recording its options. A version whose frame leaves party totals out also carries `without_party_totals: true`. The options are read as the frame refresh reads them (`datasets_api.recorded_rendering`). The body's `enrichment_stamp` is the serving code index's `enrichment_digest`, and each version carries the `enrichment_stamp` a file of it holding party-kind cells carries when rendered now: the digest when the version's frame holds a party role, and none when it holds none. The fact comes from the role columns of the output profile the version stored when it was written (`ListedVersion.holds_party_role`). A version stored without an output profile carries none when a file of it that can hold party-kind cells (`versions.carries_party_kind`) is linked under `versions.NO_PARTY_ROLE`, and the digest otherwise. The id resolves through the served-id rules, so `spec_not_found` and `identity_quarantined` apply, and a revoked version, or one whose base version is revoked, is left out. `limit` runs from 1 to 500 and defaults to 100. The body carries `next_cursor` and `complete`. The cursor resumes after the last listed version and is bound to the path id, and a cursor that does not decode or names another id refuses `request_invalid` (400).

### 6. Pin Door

Promotes rendered artifacts from the temporary working tier to the pinned retention tier and records a reference naming the caller.

| Method | Endpoint                                   | Description                                               |
| :----- | :----------------------------------------- | :-------------------------------------------------------- |
| `POST` | `/api/datasets/{id}/{content_version}/pin` | Promotes artifacts to permanent storage and links caller. |

Any caller may pin. A caller holding the `pin` grant spends only the daily pin budget (`DATASETS_PIN_DAILY_MAX`), and its reference names it by its principal label. Any other caller is an open caller. The door names it by `dfo_platform.caller.resolve_caller` (see Callers and allowances), records its reference under the caller key, and has a new pinned copy spend two further units: one of the open callers' budget (`DATASETS_PIN_OPEN_DAILY_MAX` a UTC day), whose end refuses the budget's `service_unavailable` (503, retryable after the reset, with `Retry-After` to the next UTC midnight), and one of the caller's `pin` allowance (`DATASETS_PIN_DAILY_ALLOWANCE`), whose end refuses `allowance_exhausted` (429). The door spends the daily budget, the open budget and the allowance in one transaction of conditional upserts (`datasets_api.allowance`), so concurrent pins cannot pass any of them, and a refusal by one spends none of the others. Open callers' copies spend `DATASETS_PIN_DAILY_MAX` as well, so they leave the grant's holders at least the difference. A repeat pin of an artifact that already has a pinned copy spends nothing, and a pin whose copy finds the pinned copy already made by a concurrent pin, or the working bytes gone, gives its units back (`SharedAllowanceLedger.refund_together`), so one copy spends one set of units. The share routes' pins spend the same units through the same function (`retention_admission.copy_to_pinned`): every share caller is an open caller, and each new pinned copy of a card's frame or a derived frame's root spends the daily budget, the open budget and the caller's `pin` allowance.

### 7. Exports Door

Prepares one exact frame version as a file a user keeps, and serves a link to it that only signs (`datasets_api.exports`).

| Method | Endpoint                            | Description                                                       |
| :----- | :---------------------------------- | :---------------------------------------------------------------- |
| `POST` | `/api/datasets/exports`             | Prepares a frame's file in the pinned tier and answers its facts. |
| `GET`  | `/api/datasets/exports/{export_id}` | Answers 302 to the prepared file, signed for five minutes.        |

`POST /exports` takes `{"frame": {"spec_id", "content_version"}, "format": "csv" | "xlsx" | "parquet", "bundle": bool}`, with `format` defaulting to `csv` and `bundle` to `false`, for a dataset version (`spec_`) or a derived frame (`ops_`). The export's id is `exp_` and the first 32 hex digits of the SHA-256 of the RFC 8785 form of `{spec_id, content_version, format, bundle}`. A request whose id holds a row in `datasets.export` (migration `0044_export.sql`) answers that row's facts without rendering or spending. Otherwise the door resolves the version the request names, with no fallback to another, takes a dataset version's file from the file selector's path (the listed file, else a render from the stored frame) in the long layout with the version's default enrichment columns (`analysis_roots.enrichment_columns` of the roles the version's frame holds, the columns a Spec root reads: the `_type` cells of each of `observationAbout`, `financingProvider` and `financingRecipient` it holds, beside the layout's own `_label` and `_kind` cells) or renders a derived frame's file as its file route does, copies the file to the pinned tier through `retention_admission.copy_to_pinned`, which spends the caller's `pin` allowance and the daily budgets as a pin does, and records the export. Both routes admit every caller and the website's proxy forwards both. The prepare names its caller as the pin door does, so a holder of the `pin` grant spends the daily budget alone and any other caller its own `pin` allowance, and data-mcp forwards `x-dfo-caller` and `x-dfo-caller-principal`. The 200 body carries `export_id`, `url_path` (`/api/datasets/exports/{export_id}`, relative to the public site's origin), `file_name`, `media_type`, `format`, `bundle`, `bytes`, `rows` and `columns` of the file's data table, `sha256`, `frame`, `citation`, `licences` (`source`, `label`, `licence`, `url` for each source) and `pinned`. It carries no signed URL. A CSV or xlsx export of more than 250,000 rows refuses `over_ceiling` (422), a derived frame stored without a recipe refuses `provenance_unavailable` (422), and a spent allowance refuses `allowance_exhausted` (429).

A `frame` of a dataset id alone, `{"spec_id": "spec_..."}` with 32 lowercase hex digits, exports that dataset's newest version. The door first resolves it as the analysis runner reads a Spec root of the id (`analysis_roots.newest_spec_version`), the served definition's newest version in its default enrichment, as the Presentation frames door reads a bare id. The request then runs as one naming that pair: its `export_id` is the pair's, so a bare request and a request naming the same version share one export, and the answer's `frame` names the served id and version. A bare `ops_` id, or any id off that shape, refuses `request_invalid` (400). A resolve that cannot finish refuses with a code this route registers: `service_unavailable` (503, retryable) while the version builds or for a cause a retry may clear; the cause's own code where the route registers it, such as `spec_not_found` (404) or `identity_quarantined`; `internal_error` (500) for a server fault; and `snapshot_not_found` (404) for any other cause, its own code and detail in `detail`.

`GET /exports/{export_id}` admits every caller, reads the row, and answers 302 to a URL to the pinned copy signed for five minutes, named by the file name, with `Cache-Control: no-store`. It never renders. An unknown id refuses `not_found` (404), and a version revoked since the export was prepared, or whose base version was, refuses `snapshot_revoked` (410), as every other file link does.

`licence_restrictions.json` beside the module is the licence deny-list, keyed by source ref, each value the reason its licence forbids redistribution. A source it names refuses `licence_not_redistributable` (403) at prepare, a repeat prepare included, and at the link, so listing a source withdraws its exports' links once the service is deployed with the list. The committed list is empty.

## Lifecycle and Retention

Generated artifacts default to working-tier retention and expire 30 days after initial storage. Pinned artifacts remain persisted indefinitely.

Every manifest the mint, definition, snapshot and done operation poll return carries `retention`, computed when the response is served. It reports over the frames that serve the version: a raw version's own frame, and a derived version's own frame, when its record says what that frame holds, then its base version's. It reads `{"pinned": true}` when any of those frames has a pinned copy, and otherwise `{"pinned": false, "held_until": ...}`, the latest of their `stored_at` plus 30 days. A download of a frame after `held_until`, while its bytes survive, renews it for 30 days. Pinning a version also pins the first of those frames, servable or aged, whose bytes survive.

A version's `prepared_at` is written once at its first mint and stored with the version record. Every re-mint and re-render reads the stored value, so the date in a bundle's `README.md`, `CITATION.cff` and file name stays fixed.

A download link redirects to a URL signed for five minutes. The artifact store reuses a signed URL for at most one minute (`SIGNED_URL_REUSE_WINDOW`), so a redirect carries at least four minutes.

Synchronous materialisation admits on an exact `series_coverage`-based estimate (rows, SDMX requests) computed before any network call. A request whose estimate stays at or under both `DATASETS_SYNC_BUDGET_ROWS` and `DATASETS_SYNC_BUDGET_REQUESTS` (the sync budget) runs inline; an xlsx request whose estimate already exceeds Excel's row limit refuses pre-fetch, with problem code `excel_limit`.

## Async operations and the worker

A mint or definition request over the sync budget is recorded as an operation (`datasets.operation`) instead of running inline: the door answers `202 Accepted` with a `Location` header and an `OperationEnvelope` (`operation_id`, `status`, `poll`, `retry_after_ms`). The operation id is derived deterministically from the request identity (the subject id and, for a definition, the members the submitting door resolved, which the worker resolves again, failing the operation `upstream_version_changed`, retryable, when they differ, so a resubmission starts a new operation for the new members), the origin catalogue build bound to the request, and the rendering key of `options` (format/groupby/pivot/columns/...), so two requests for the same subject that differ only in rendering get distinct operations, a rendering-caused deterministic failure never fails a resubmit asking for a different rendering, and a new catalogue build, which can admit different provenances, starts a new operation. A coverage build leaves the id unchanged, so a done operation stays reachable. The row records that build as `origin_catalogue_build_id`. An estimate over `DATASETS_ASYNC_MAX_ROWS` or `DATASETS_ASYNC_MAX_REQUESTS` refuses `over_ceiling` before any operation is recorded, and a new operation, or the reset of a recorded one, at `DATASETS_OPERATION_BACKLOG_MAX` (default 20) other live rows, the `pending` and `running` rows that are not abandoned, refuses `service_unavailable` (503, retryable, `Retry-After`) unless the subject's head, read again after the refusal, now answers the request, as it does when the operation's own run completed in between; a resubmit that joins a live operation is exempt. One Cloud Tasks task is created per submission: the submit commits the `pending` row, creates the task, then records `dispatched_at`. An enqueue that fails or times out leaves `dispatched_at` null, and a poll 30 seconds or more after the submission creates the task again under the same name. Cloud Tasks deduplicates by name, and `AlreadyExists` counts as success. `GET /api/datasets/operations/{op_id}` polls it: `pending`/`running` answers 200 with progress, `done` answers 200 with the same manifest shape a synchronous mint returns, each artifact under its download link, listing the artifact for the rendering its request posted plus statistics artifacts, and `failed` answers `operation_failed` (500) with the operation's refusal code in `cause.code` and its stored `retryable` flag. A deterministic failure also stores the refusal the worker classified (`datasets.operation.refusal`), and the poll body carries its `detail`, `pointer`, `alternatives`, `issues` and ceiling fields. A `done` operation whose rendering the snapshot lists no artifact for (a bundle linked only as incomplete, a bundle of a superseded rendition, an expired working-tier artifact) is failed `internal_error`, retryable, by that poll and answered `operation_failed`, so a resubmit of the identical request re-runs it. The poll carries no principal check in any state: a `done` manifest is the one the public mint returns and the public snapshot route lists for any caller. A `running` operation whose lease has ended (`claimed_at + lease_seconds`) is failed `internal_error`, retryable, by the next poll when the task's final delivery claimed it. One claimed by an earlier delivery polls as `running` until the next delivery claims it. That operation, and a `pending` one, are failed the same way once `DATASETS_OPERATION_DEADLINE_SECONDS` have passed since the dispatch, or the submission when no dispatch is recorded. A task delivery that arrives after that deadline fails the operation the same way without running it, and the daily `datasets-maintenance age-operations` job does so for every such operation, polled or not. A resubmit of the identical request resets a `done` operation, a failed-retryable one, or a `running` one whose lease has ended, to a new submission. Terminal operations stay pollable for `operation_retention_days` (published on `/api/datasets/capabilities`); the same job then deletes `done` and `failed` rows last updated longer ago, and a poll for one answers `operation_not_found`.

A dedicated worker process, built from the same image with `DFO_WORKER_SURFACE=1`, mounts a single internal route (`POST /internal/datasets/operations/{operation_id}/run`) that Cloud Tasks dispatches to, verified by Cloud Run IAM plus an app-level OIDC check. It claims the operation for the submission the task names, with a static lease of 1,620 seconds (`claimed_at + lease_seconds`, under the task's 1,800-second dispatch deadline). A task from an earlier submission answers 200 `superseded`, and a delivery that finds another attempt inside its lease answers 409. Each claim increments the operation's attempt counter, and every later write of the run is fenced on that attempt, so a worker whose lease ended and was reclaimed can no longer write. The operation's own writes carry the attempt in their `WHERE` clause, and the head advance checks it under a share lock on the operation row inside the head's transaction (`HeadFence`), so a run that lost the operation after its version and artifact writes leaves the head and `datasets.materialisation` unchanged and answers 200 `superseded`. The run has a work deadline 1,500 seconds after the claim, checked before the version record and before each artifact render and upload, so a run past it releases without writing. The head advance has no deadline check, since the fence covers one that falls after the deadline and inside the lease. The run takes one materialise permit from the worker process's single-permit semaphore. It reads the published coverage pointer and loads a moved build before it starts, re-estimates the request against that snapshot, records the estimate on the operation, fails `over_ceiling` if the fresh estimate now exceeds the async ceilings, and sizes its fetch guard from it. The run completes the operation only when a snapshot read of the completed version, narrowed to the request's rendering, lists an artifact other than statistics. Otherwise it takes the transient-failure path below. Each finished chunk writes `rows_written`, fenced on the attempt. A refused write stops the run at its next chunk, and it writes nothing more and answers 200 `superseded`. A worker that dies mid-run leaves its lease to end, after which the task's next delivery reclaims it, or, when the dead delivery was the task's last, the next poll fails it retryable. A transient failure before the operation's last Cloud Tasks attempt (`X-CloudTasks-TaskRetryCount` against `DATASETS_OPERATION_MAX_ATTEMPTS`, 3 by default, mirroring the queue's own `retry_config.max_attempts`) releases the operation back to `pending` before answering non-2xx, so the next retry claims immediately. On the last attempt it marks the operation failed instead. `docs/datasets-sync-ceiling.md` covers the full admission, operation, and worker mechanics, including the env vars each side needs and the measured writer memory numbers.

## Currency and the Subject Head

`datasets.version_record` (`dataset_store` migration `0004_version_records.sql`) is immutable: one row per `(subject_id, content_version)` pair, written once and never updated. It has nowhere to say which of a subject's own recorded versions is the one a `GET` should currently serve.

`datasets.subject_head` (migration `0009_subject_head.sql`) is that pointer: one mutable row per `subject_id`, carrying the subject's current `content_version`, when that pointer was last `confirmed_at`, when it was `materialised_at`, and the producing run's `materialisation_id` and dependency fingerprint (`dependencies`, migration `0027_materialisation_record.sql`). The fingerprint (`materialise.dependencies`) holds a digest of the sorted member dcids, each dispatched provenance and each rate-table provenance with its `lastDataRefreshDate`, each conversion recipe with the digest of its deployed body, and the window an open-ended range read. The graph serving revision is not part of it, since it moves on every graph restart. The `signal` column keeps its default and nothing reads it.

`datasets_api.version_store.LiveHeadStore.advance_head` takes the run's `MaterialisationRecord` and the `materialisation_id` of the head its caller read (`expected_materialisation_id`, `None` for no head). In one transaction it inserts the run's `datasets.materialisation` row and applies the head write only while the stored row still names that run: `INSERT ... ON CONFLICT (subject_id) DO UPDATE ... WHERE datasets.subject_head.materialisation_id IS NOT DISTINCT FROM %s`, `IS NOT DISTINCT FROM` so a first insert with no existing row applies and a head that names no run matches `None`. A write whose expected run has already moved returns `None`, keeps its run's row, and leaves the head untouched. Every writer reads the head once before deciding what to write: `datasets_api.current.serve_current` passes the head it read as `expected_head` to `serve_definition`, which advances the head after the version record commits, so the head names the run that produced it. On `None`, `serve_current` re-reads the head and stamps the response with the winner's confirmation. An operation run also passes its claim, the operation id and attempt (`HeadFence`). The same transaction then first takes a share lock on the `datasets.operation` row and checks that it is still `running` at that attempt. When it is not, `advance_head` raises `HeadFenceLost` and writes neither the materialisation row nor the head. The lock conflicts with a claim's update, so a claim that races the advance either commits first, and the advance refuses, or waits until the advance commits. A request that is not an operation run passes no fence.

`ServeDeps.head_store` (type `HeadStore`), injected through `datasets_surface(head_writer=...)` the same way `version_writer` is, writes the head once a run's version record has committed. Every rebuild in `serve_current` advances it, for the mint, `GET /api/datasets/{id}`, `/options`, the frame refresh and the operations worker alike, so a repeat mint of a current head is served from it with no SDMX call and the next GET after a worker run is a head hit. Every one of these keys the head on the served definition's id (`datasets_api.kinds.spec_id.resolve_served_definition`), the canonical form of the posted identity, so a GET under a non-canonical posted id serves the head its mint wrote. `ServeDeps.materialise_semaphore` (`DATASETS_MATERIALISE_MAX_CONCURRENCY`) bounds concurrent `materialise_group` calls across mint, definition retrieval, and the options route's rebuild, whichever door calls them.

`GET /api/datasets/{id}` and its `/options` sibling read the head before deciding whether to serve the stored record or rebuild it. A head confirmed within `DATASETS_HEAD_RECHECK_SECONDS` (default `900`, fifteen minutes) is served as stored, with no read. Past that interval, one `node_arcs_many` read of every stored source and rate-table provenance's `lastDataRefreshDate` rebuilds the fingerprint against the members the request resolved, the deployed recipe bodies and the clock, and `dependency_changes` compares it with the head's member by member: a match refreshes `confirmed_at` and serves the stored record with no SDMX request, a difference re-materialises and advances the head. A provenance with no refresh date compares equal to itself, and a head written with no fingerprint rebuilds once. `DATASETS_HEAD_MAX_AGE_SECONDS` (default `86400`, twenty-four hours) counts from the head's last materialisation, not from a confirmation: past it the frame re-materialises regardless, which catches a value correction with no date move, a newly elected provenance, a catalogue build that admits or withholds a source, and sources with no date. A run whose member StatVars the origin catalogue names DFO alone as holding, and whose provenances, rate tables included, it lists as DFO's, records in its fingerprint the bound graph release's import key (`imported_data`, `graph_release.views.imported_data_digest`): the import execution id, the hashes of the platform parts, the hash of the `code_index_blocks` part, and the role axes and build year the coverage view takes from the `declarations` part. A composite records the key its components share, and none when they differ, and records the digest of the composite declaration it was composed by (`composites`), which the fingerprint check compares with the declaration deployed now. Every import that lands in our Spanner moves the key, and a builder, declarations text, `base_parties` or DC serving revision change that moves only the release id leaves it alone. A StatVar base Data Commons or the UN also holds records no key, since a facet of theirs could win its election with no import of ours, and so does a run whose election ranked any candidate outside DFO's provenances or whose default place scope was a countries fallback that request alone took. Past the recheck window the head rule runs the catalogue test again over the head's StatVars and sources, so a catalogue built since that lists base beside DFO rebuilds a keyed head with `rebuild_reason` `imported_data`. The process rate-table cache keys on the import key too, so a table re-imported on the same day is fetched again. Such a head rebuilds as soon as the bound release carries another import, with `rebuild_reason` `imported_data`, and otherwise serves past `DATASETS_HEAD_MAX_AGE_SECONDS` up to `DATASETS_HEAD_IMPORTED_DATA_MAX_AGE_SECONDS` (default `604800`, seven days), which bounds a Spanner edit that lands no import and a catalogue change no import carries. A materialiser deploy moves no key, so a change to what the materialiser writes for unchanged inputs must bump `DEPENDENCIES_SCHEMA` (`materialise/dependencies.py`) for keyed heads to rebuild before that limit. A head over a base Data Commons or UN source, whose rows change without an import of ours, records no digest and keeps the twenty-four-hour limit, as does a head written before runs recorded one. A mint reads the head the same way before admission, so a repeat mint of a current head that links the requested rendering answers from it without estimating or submitting an operation. Each serve's `datasets.timings` line carries `rebuild_reason` (the fingerprint members that differed, `schema`, `imported_data`, `max_age`, `no_head`, or `unservable`; absent when served from the head), `sdmx_requests`, `graph_requests`, `db_transactions`, `sign_blob_calls` and `permit_wait_ms`, and its `Server-Timing` header carries each count as `name;desc=n`. `sdmx_requests` counts every SDMX request sent, hedge duplicates included, and a read that hedges adds `sdmx_hedges`, the duplicates' share, and `sdmx_hedge_wins`, the duplicates whose 2xx CSV response won. A first mint makes at most six store transactions, holding one connection at a time: the registry's read, registration and read-back of the definition, one head read, one write transaction for the version record and every artifact's inventory row and link, and one for the materialisation row and the head advance. A head hit inside the recheck window makes three: the definition read, the head read, and one read of the version, its revocation and its locations. Neither signs anything. The options route runs the identical decision with no rendering. A match confirms the head, and a rebuild records the version, its canonical frame and statistics, and advances the head. A head inside the recheck window serves from the read executor only when it already holds the requested rendering. Rendering a missing format from the stored frame (the version's canonical Parquet frame, or else its frame1 document) runs on the work executor.

Both routes report the outcome on the manifest's `trace`, documented in `docs/conformance-datasets-api-v1.md`. `served_from` is `head` when the stored record was served, either as recorded or after a matching fingerprint, and `materialise` when this request rebuilt the frame. `confirmed_at` is the UTC timestamp of when that currency was last established. On definition retrieval and the options route a fingerprint match moves it forward. `content_version` keeps its documented meaning. It is a digest of the canonical frame bytes alone, so a currency check moves it only when the rows move. `confirmed_at` and `served_from` are the currency-facing fields.

A `done` operation poll reports the same pair as a synchronous mint that materialised: `served_from` is `materialise` and `confirmed_at` is the instant the run confirmed the subject head, which `OperationStore.complete` records on the row (`datasets.operation.confirmed_at`, migration `0032_operation_confirmed_at.sql`). A row completed by an image that records no such instant carries neither field. Snapshot retrieval, `GET /api/datasets/{id}/{content_version}`, also carries neither: it reads one stored version and makes no currency judgement.

Neither route accepts a caller-supplied force-refresh flag. `Cache-Control: no-store` is already sent on every response, so nothing downstream caches a stale body past its own currency window. `GET /api/datasets/{id}/{content_version}` already covers a caller who wants one exact, pinned result with no currency question at all. A client-triggered rebuild would also let any caller pay, on demand, the cost `DATASETS_MATERIALISE_MAX_CONCURRENCY` exists to bound, defeating it.

### Frame refresh

`POST /api/datasets/frames/refresh` takes `{"spec_id", "content_version"}` naming a dataset frame and answers whether that frame is still the current frame of its rendering. It runs the currency check above with the head confirmed or advanced as `GET /api/datasets/{id}` does, and every answer is a 200:

- `{"status": "current", "frame": {"spec_id", "content_version"}}`: the named frame is current.
- `{"status": "moved", "frame": {"spec_id", "content_version"}}`: the current frame of the same rendering has another `content_version`, whether this call rebuilt the dataset or an earlier one did.
- `{"status": "pending", "operation_id", "retry_after_s"}`: the rebuild is over the inline budget and runs as a queued operation. A call made while it is queued or running names the same operation and enqueues nothing, and a call after it completes answers `moved` or `current`.

The dataset and rendering come from stored records. A version with no `base_content_version` is the dataset's default rendering. A derived version, a groupby collapse or a party-totals cut (`without_party_totals`) or both, names its raw version in `base_content_version`, and the options that minted it are read from the requested-format file linked under it (`datasets_api.recorded_rendering`). For a derived version the answer is the derived version under the current head with the same options, looked up among the stored versions and rendered from the head's stored frame when none is recorded yet. A rebuild mints bare frame-layout parquet with the frame's groupby and party-totals cut, which writes the canonical frame Presentation reads, so a frame minted without its totals refreshes to a frame without them. The route records no reference and pins nothing.

A groupby sum that leaves the frame unchanged, as over a dataset with one contributing StatVar, and a party-totals cut that leaves nothing out have no version of their own, and their file is linked under the raw version. A raw version linking such a file and no plain requested-format file refreshes as that rendering. One linking both stands for two renderings. While that rendering of the current data is still the plain frame the refresh answers with it and links both files under it, and once it has a version of its own the refresh refuses `rendering_not_recorded`.

A rebuild over the inline budget submits the request's operation. The submission resets a `done` operation and enqueues it again, so the refresh answers `pending`, and the worker's run advances the head, so a later refresh answers from that head.

Refusals: `refresh_not_permitted` (403) for any caller but the live-refresh principal, checked before the body is read. `spec_not_found` (404) for an unregistered id and `snapshot_not_found` (404) for an unknown version of a registered one. `frame_not_refreshable` (422) for a derived (`ops_`) frame. `rendering_not_recorded` (422) for a derived version with no linked file recording its options, for a raw version that links a plain file and one or more groupby sums or party-totals cuts once those renderings of the current data differ, and for a raw version with no plain file, or a derived version, that links files of two or more different options, whose records do not say which the frame is. A cut and a groupby that left the cut frame unchanged share one version and are two such options. `request_invalid` (400) for a malformed body. `service_unavailable` (503, retryable) when the refresh door's executor is full, a materialise slot is not free within `DATASETS_MATERIALISE_WAIT_SECONDS`, a shared rebuild is still running at the request deadline, or the operations backlog is full. `internal_error` (500) when the queued rebuild failed without a retry. A rebuild that runs inline refuses as `GET /api/datasets/{id}` does.

The route shares the definition door's clients and deadline (`DATASETS_DEFINITION_TIMEOUT_SECONDS`) and runs on the work executor (`DATASETS_WORK_MAX_CONCURRENCY`) beside mints and rebuilds, so a burst of refreshes occupies work threads only and leaves the read executor's threads to head hits. A refresh arriving when every work thread is busy refuses `service_unavailable` (503, retryable).

### One rebuild per dataset

Concurrent definition reads and frame refreshes that need a head-advancing rebuild of one dataset run one materialisation (`RebuildFlights` in `datasets_api/admission.py`). The first caller rebuilds. Each other caller waits until its own request deadline, then reads the head again and is served from it, or refuses `service_unavailable` (503, retryable) when the rebuild is still running at that deadline. When the rebuild ends without advancing the head, because it failed or its request was abandoned, each waiter rebuilds for itself and answers with its own result or refusal, and no waiter inherits the failure. The first of them is the rebuild later arrivals wait on. The scope is one process. Two instances can rebuild one dataset at the same time, and the result is correct. Version inserts are `ON CONFLICT DO NOTHING` and `advance_head` is a compare-and-swap, so the second writes nothing new. Mints, the options route and frame refreshes use the same `RebuildFlights` as definition reads. The operations worker runs in its own process with its own `RebuildFlights`, so it takes no turn with the API's rebuilds.

## Origin provenance

Each request, and each worker operation, binds one origin catalogue build (`ORIGIN_CATALOGUE_URI`, see `deploy/origin-catalogue.md`). The worker runs an operation under the build its row names when that build is the one it has loaded, and otherwise reads the published build before it claims, so an operation never runs under a build older than the one it was submitted under. Every graph read goes through the origin graph client (`origin_catalogue.graph`), which drops facets whose provenance the catalogue does not admit. The manifest reports that build in three places.

- `citation.sources[]` entries carry `source` (`{ref, label}`, the Data Commons `Source` node behind the provenance, or for a UN System Data Commons series the agency provenance itself) and `data_commons` (`{id, label}`, with `id` one of `dfo`, `base`, `un_system`). `label`, `url`, `source` and `data_commons` come from the catalogue's provenance table and `license`, `license_type`, `license_url` and `documentation` from the graph (`materialise.provenance_doc.read_source_citations`). `documentation` is the source's `read_provenance_doc` content as read at first mint, `null` when the graph documents nothing for the source or that read failed, and it feeds the bundle's `README.md` and `SOURCES.md`. A bundle render of a version already on record fills every stored `null` source field except `ref`, `label` and `processing_level` (`license`, `license_type`, `license_url`, `url`, `source`, `data_commons` and `documentation`) from a live read, built as a first mint builds it (`datasets_api.manifest.cited_source`), for that render only and only when no servable bundle is linked under the request's rendering key. Every set field stands, and a source with every field set reads nothing. A mint leaves the stored body as it is. A bundle whose documentation or code label read failed is linked to the version as incomplete: its `rendering` carries `"metadata": "incomplete"`, its download link resolves and its digest can be pinned. No request's rendering key matches it, so the next request for the bundle renders and reads again and links a complete bundle beside it. A snapshot lists an incomplete artifact only when it is pinned, after the current artifacts, and lists bytes also linked under the complete rendering once, without the marker. A provenance the table does not list, such as a DFO provenance newer than the loaded build, is named from the graph and carries `source` and `data_commons` as `null`.
- `trace.origin_catalogue_build_id` names the build that admitted the data. A version minted before the catalogue existed keeps serving as minted, with neither the trace member nor the citation members, so its absence marks a pre-catalogue version.
- `trace.family_member_digest` and `trace.family_member_count` state every member the identity admits, before antichain reduction, by the digest Search's `resolved.shape.member_digest` uses. `trace.resolved_stat_vars` lists the members served. Both fields are null when member resolution did not read the whole family, which is a graph walk whose candidate page was truncated. `trace.stub_candidates` lists, as `dcid:` refs, the candidates a graph walk under a confirmed root left out of the family because its reader holds their arcs complete and they carry none of the arcs that define a StatVar (`typeOf`, `populationType`, `measuredProperty`, `statType`, `measurementQualifier`, `measurementDenominator`, `constraintProperties`, `observationProperties`), though the reverse read placed them in the family (`MemberGroup.stub_candidates`); the key is omitted when there are none. They stay out of `content_version`, so an answer from a stored version carries the trace recorded when that version was first stored: the fields describe the family at that mint, and both keys are absent on a version stored before they existed. Read an absent key and a null alike as unknown.
- `warnings` carries `origin_catalogue_stale` when the build is more than 14 days old; `un_system_unavailable` naming the places the UN System Data Commons refused or failed to read; and `withheld_by_registry` when a subject entity (a bound one, or for a request that binds no entity a country under Earth) came back with no rows, has no admitted data at all, and a provenance the catalogue withholds holds data there, naming those entities and the withheld provenances. A mint that lands on a version already on record adds this call's warnings to the stored body and replaces the stored `origin_catalogue_stale` entry with this call's.

When no member's facet probe returns a candidate, the mint serves the empty result: a 200 manifest with `coverage.rows` at 0, `empty_result`, no facet selection and no cited source (`MaterialisationResult.probe_empty`). `prewrite_definition` first runs `origin.refuse_unserved_empty_probe`, which refuses before anything is written in two cases. When every facet for a subject-only member's variable at its places is withheld, the request refuses `excluded_by_registry` (422) naming the withheld provenances. The refusal names the variables of the read that found withheld data. A UN member with no candidate at places the UN refused or failed to read refuses `upstream_error` (502, retryable) naming those places, since its empty probe says nothing about data there. A UN member that binds no entity covers every country, including the few the UN front door refuses on every read, so it refuses `upstream_error` only when a UN read failed. With no data anywhere else it is the empty result, and its `un_system_unavailable` warning names the refused places. The refusal names the first five places and counts the rest. The facet probe runs before the mint doors open the origin record, so the probe carries what its UN reads could not serve and the materialisation adds it to that record: the refusal and the `un_system_unavailable` warning are the same at the mint doors and the worker. Both `excluded_by_registry` and `withheld_by_registry` cost a facet read with no domain filter, made only when a requested series left an entity without rows, and under the request's deadline and a 16 MiB response cap (`datasets_api.origin`). The warning takes one read, and the refusal one read per distinct list of entities among the subject-only members. On an empty probe a re-read that fails or passes the cap refuses `upstream_error` (502, retryable), and one the deadline ends refuses `timeout` (504), so no empty version or head is written unless the check completed. A member whose candidates leave a facet axis without a default (`default_facet_undefined`) gets the same two checks for that member alone (`origin.refuse_unserved_selection`) and refuses `upstream_error` or `excluded_by_registry` in its place. For a `default_facet_undefined` refusal and for the warning, a failed re-read leaves the answer without the explanation. A subject-only request that binds no entity is re-read at the countries under Earth, and for the refusal at Earth too, the places its facet probe read. The check on an empty probe reads those countries again, and a failed read refuses `upstream_error` (502, retryable). A UN member that binds none refuses on a failed UN read before that read, since its probe read only Earth and its countries. For such a request nearly every mint leaves a country without rows, so nearly every mint makes the re-read. The warning takes the countries from the materialisation result, so a mint reads containment once, in its facet probe. Role-bearing requests and `ContainedIn` scopes are not re-read, because role-bearing series are DFO's and always admitted, and a scope's members are unknown before the read.

For a variable both DFO and base Data Commons hold, facet selection ranks DFO's facet first when it covers at least as many requested places as the broadest base facet (`selection_reason` `dfo_precedence`); a broader base facet serves every place it holds, DFO's places included, so a population request for every country serves World Development Indicators' 169 countries over OECD DAC1's 50 (`docs/datasets-facet-policy.md`). Admission keeps both origins' facets at every place, and one facet group serves the request. The ranking applies to the facets left after narrowing by the spec's bound axes and its native-currency preference. A spec that binds a provenance, unit or measurement method only one origin's facet carries gets that facet at every place it holds.

A request binding one place breaks a tie between facets equal on count and latest date on each facet's places across the whole variable, read from the variable's facet profile only when the tie decides the provenance, method, unit or cadence served (`docs/datasets-facet-policy.md`). When that read fails, a mint, definition rebuild or operation refuses rather than store the facet the unit's name would pick: `service_unavailable` (503, retryable) for a transient failure (a timeout, a graph read error or byte cap, a refused profile flight), and `internal_error` (500, not retryable) when the variable's own profile raised for any other reason, a defect logged as an error with the variable. An operation fails such a defect at once. Search answers the same tie on the unit's name and marks the answer degraded.

The components envelope (`assembler.mint.provenance`) carries the same pair on each `provenance.sources[]` item as `source: {id, name}` and `data_commons: {id, name}`, left out where the citation entry has none.

## Trust Boundary

Callers reach the API through the website's proxy, which counts each IP's calls in a fixed window kept in Postgres and shared by every proxy instance, answers `429` past the allowance (120 calls a minute on `/api/*` by default), lets a call through when the count fails, and passes `Authorization` upstream unread. The deployment bounds request bodies, and publish also checks its own `Content-Length` ceiling at admission, before it reads the body.

The Datasets API requires a grant only on the Publish and recipe doors (`POST /frames/publish` and the recipe routes) and the frame refresh. `datasets_api.principals` reads the configured principal header (`DATASETS_PRINCIPAL_HEADER`, default `x-dfo-principal`) into the grants its value holds: `pin` for `DATASETS_PIN_FIRST_PARTY_PRINCIPAL`, `publish` for `DATASETS_FIRST_PARTY_PRINCIPAL`, `refresh` for `LIVE_REFRESH_PRINCIPAL`, and `share_import` for `PRESENTATION_SHARE_IMPORT_PRINCIPAL`, which opens only the Presentation share import route. Each of those routes requires one grant and refuses a caller lacking it with 403 before the body is read. The Pin door (`POST /{id}/{content_version}/pin`) reads the header too, before the body, and admits every caller: the `pin` grant decides whether a pin spends the caller's allowance (see Pin Door). Pinning and publishing take two independent values, since pinning has no unpin or delete route on this surface and a principal trusted to publish must not automatically gain the pin grant too.

The frame refresh (`POST /frames/refresh`) admits one principal of its own, `LIVE_REFRESH_PRINCIPAL`, in the same header. Every principal is compared in constant time (`datasets_api.principals`), an unset or empty value refuses every caller with `refresh_not_permitted` (403), and the refresh grant opens no publish, recipe, or pin route. The Presentation render routes take the same principal through `datasets_api.live_refresh.LiveRefreshPrincipal`.

Each of the three principals is a shared secret the calling service puts in the header itself: `ai` sends `DATASETS_FIRST_PARTY_PRINCIPAL` on a publish and on the recipe routes, the website sends `DATASETS_PIN_FIRST_PARTY_PRINCIPAL` on its server-side pin call, and the website and `ai` send `LIVE_REFRESH_PRINCIPAL` on the frame refresh and the Presentation render routes. Nothing in this service or in front of it sets, replaces, or removes the header, so knowing a value is what admits a caller. Each service holds its value server-side and it must not reach a browser.

The recipe door admits the publish principal on all three of its routes. `PUT` and `GET /frames/{spec_id}/{content_version}/recipe` write and read the recipe of a published derived frame, the op-spec tree that produced it, and `GET /recipes/replays/{replay_key}` returns the frame stored under a replay key. A publish may also carry the frame's `recipe`. A series a recipe's `anchor.left_out` names carries its `root`, the index of the population it belongs to in the order of the recipe's populations (one per root dataset), and its `coordinates`, and its `label` is optional. The coordinates must name the series. They hold `stat_var` or at least one entity-role column, which is any column other than `stat_var`, `time_period`, `value`, `unit`, `status`, `measurementMethod`, and `provenance`. Empty coordinates, and coordinates of only those other columns, refuse `request_invalid` (400) on a publish and on `PUT .../recipe`. Recipes live in `datasets.frame_recipe`, outside the version lineage a republish is compared on, so a republish may add one or omit one. A pair keeps its first recipe. A later write with a different `normal_form_hash` or `replay_key`, or with a `replay_key` another frame holds, refuses `publish_conflict` (409). An analysis run whose own pair holds no frame answers the servable frame its replay key names. When that frame's file is no longer served, the stored recipe gives up the key (`RecipeStore.supersede_replay`, migration `0043_frame_recipe_superseded.sql`) and the run publishes under its own pair, which takes it. The old recipe is still read by its pair.

`datasets-maintenance normalise-recipes [--dry-run]` runs by hand once per environment, after the website's share migration job has imported its shares through the Presentation share import route. A recipe written before the analysis route sorted root columns lists a root's `options.columns` in the order its client sent them, so the same tree run on this service computes another `normal_form_hash`, and a live share's derived card stays on its original frame, stated stale. For each such row of `datasets.frame_recipe` the task sorts each root's columns and lists each once, recomputes `normal_form_hash` and `replay_key` with the functions the analysis route uses (`dfo_analysis_engine.recipe`), moves every card revision drawing that frame from the old hash in its `frame_rendering` to the new one (`presentation_store.store.rehash_derived_rendering`), and then rewrites the recipe row, its body's two hashes included. The Presentation and Datasets databases commit separately, revisions first, so a run stopped between the two leaves the recipe to the next run. It skips a recipe whose stored hashes it cannot compute again from the stored recipe (`unreproducible`, as for a tree whose frames different engine builds computed) and one whose new replay key another frame's recipe holds (`replay_key_held`), with one `datasets_recipe_normalise_skipped` `WARNING` line each, and leaves both as they are. It writes one `datasets_recipes_normalised` line counting the recipes normalised, the revisions moved and each kind of skip, and exits 1 when it skipped any. `--dry-run` counts the same and changes nothing, and a second run changes nothing. A Presentation instance that loaded a derived frame before the run keeps its old hash in its frame cache until it restarts.

### Callers and allowances

A write that counts against an allowance names its caller with `dfo_platform.caller.resolve_caller`, which lives in `dfo_platform` so every surface names callers one way. A caller key is `ip:` and the first 32 hex digits of HMAC-SHA-256, keyed by `DFO_CALLER_HMAC_KEY`, over the client address folded as the website folds it: IPv4 as written, an IPv4-mapped IPv6 address as its IPv4 form, and any other IPv6 address as its /64 (`2001:db8::1` hashes `2001:db8:0:0::/64`). The website computes the same key with the same secret (its `CALLER_HMAC_KEY`), so a client has one key whether it calls through the website or directly, and no raw address is stored.

A request whose `x-dfo-caller-principal` header matches `DFO_CALLER_PRINCIPAL`, compared in constant time, comes from the website, and its caller is the one `x-dfo-caller` names. With the secret matched and no single well-formed `x-dfo-caller`, the request refuses `request_invalid` (400), since counting it by address would put every client of the site on one allowance. A request that carries `x-dfo-caller-principal` without matching it, or while `DFO_CALLER_PRINCIPAL` is empty, refuses `service_unavailable` (503, not retryable) and logs the mismatch at ERROR, naming neither value. A request with no `x-dfo-caller-principal` is named from the X-Forwarded-For entry `DFO_TRUSTED_PROXY_HOPS` places from the right (default 0, the entry Cloud Run appends). `request.client` goes unused, because `ProxyHeadersMiddleware` sets it from the leftmost entry, which the client writes. Without `DFO_CALLER_HMAC_KEY`, or when that entry is missing or not an IP address, the write refuses `service_unavailable` (503, not retryable), since counting every caller under one key would give them one allowance.

`datasets_api.allowance` keeps each caller's spending in `datasets.caller_allowance` (migration `0039_caller_allowance.sql`), one row per caller key, kind and UTC day. A spend is one upsert that adds one only below the limit, so concurrent spends cannot pass it. A spent allowance refuses `allowance_exhausted` (429, not retryable) with `Retry-After` counting the seconds to the next UTC midnight, when every allowance resets. A pin's unit stays spent when the copy it admitted stands and a later step fails, and a share or card write that fails gives its unit back (`allowance.spending`). The kinds are `pin` (`DATASETS_PIN_DAILY_ALLOWANCE`, default 100), `share` (`DATASETS_SHARE_DAILY_ALLOWANCE`, default 10) and `card` (`DATASETS_CARD_DAILY_ALLOWANCE`, default 500, migration `0042_caller_allowance_card.sql`).

| `DATASETS_SDMX_BASE_URL`             | Upstream SDMX client base URL for member queries.                                                                                                                                                                                                                                                             |
| `DATASETS_ARTIFACT_BUCKET_WORKING`   | Google Cloud Storage bucket name for working-tier rendered artifacts.                                                                                                                                                                                                                                         |
| `DATASETS_ARTIFACT_BUCKET_PINNED`    | Google Cloud Storage bucket name for pinned permanent artifacts.                                                                                                                                                                                                                                              |
| `DFO_PUBLIC_SITE_URL`                | The public website origin, such as `https://developmentfinance.org`, which also proxies `/api/*`. Every bundle link is built on it, and the presentation components door reads it too. The datasets surface and the worker refuse to start without it, and a value with a path, query or fragment is refused. |
| `GRAPH_RELEASE_URI`                  | Base URI of the published graph release this surface and the worker serve from (`gs://` or `file://`); each request and operation binds the release the pointer names. A missing or unopenable release fails startup; see `deploy/graph-release.md`.                                                          |
| `ORIGIN_CATALOGUE_URI`               | Base URI of the published origin catalogue this surface and the worker load at startup; each request binds the loaded build, and each worker operation the published one.                                                                                                                                     |
| `DFO_WORKER_URL`                     | The worker service's own base URL; enqueued as the Cloud Tasks OIDC audience.                                                                                                                                                                                                                                 |
| `DFO_WORKER_INVOKER_SERVICE_ACCOUNT` | Service account the worker's run route accepts as the OIDC token's `email` claim.                                                                                                                                                                                                                             |
| `DFO_TASKS_QUEUE`                    | Cloud Tasks' fully-qualified queue resource name this surface enqueues over-budget operations onto.                                                                                                                                                                                                           |
