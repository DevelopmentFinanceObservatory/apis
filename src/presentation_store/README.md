# presentation_store

`presentation_store` provides PostgreSQL persistence and frame management for the assembler subsystem. It manages components, compositions, and resolved series coordinates within the `presentation` schema, and coordinates frame resolution and artifact pinning across dataset services.

## Architecture and Responsibilities

The package exposes two primary adapters implementing `assembler.ports`:

```
+---------------------------------------------------------------------------------------------------+
|                                             assembler                                             |
+-------------------------------------------------+-------------------------------------------------+
                                                  |
                         +------------------------+------------------------+
                         |                                                 |
                         v                                                 v
+-----------------------------------------------+   +-----------------------------------------------+
|                LiveFrameStore                 |   |             LivePresentationStore             |
|         (assembler.ports.FrameStore)          |   |        (assembler.ports.RevisionStore)        |
+-----------------------+-----------------------+   +-----------------------+-----------------------+
                        |                                                   |
        +---------------+---------------+-------------------+               |
        |               |               |                   |               v
        v               v               v                   v   +-----------------------+
+---------------+ +-----------+ +---------------+ +-----------+ |     dataset_store     |
|   Snapshot    | | Artifact  | |   Reference   | |   Graph   | |  (ConnectionPool for  |
|    Reader     | |   Store   | |    Writer     | |  Reader   | | presentation schema)  |
+---------------+ +-----------+ +---------------+ +-----------+ +-----------------------+
```

1. `LivePresentationStore`: Implements `assembler.ports.RevisionStore`. Executes transactional reads and writes over `presentation.*` tables, manages composition blocks, and records revision history.
2. `LiveFrameStore`: Implements `assembler.ports.FrameStore`. Resolves frame references (`FrameRef`), fetches content-addressed artifacts, computes structural views, resolves display labels, and pins frames to retain backing data.

## Identity Generation

Component and composition identifiers use 26-character Crockford Base32 Universally Unique Lexicographically Sortable Identifiers (ULIDs) generated by `presentation_store.ids`.

Each ULID contains a 48-bit big-endian millisecond timestamp and 80 bits of cryptographic entropy (`os.urandom`).

- Component IDs (`mint_component_id`): `cmp_` prefix (e.g. `cmp_01ARYZ6S41YYYYYYYYYYYYYYYY`).
- Composition IDs (`mint_composition_id`): `cps_` prefix (e.g. `cps_01ARYZ6S41ZZZZZZZZZZZZZZZZ`).

An id grants read of its draft. The 80 random bits keep ids from being guessed or enumerated. An id that names no row raises `assembler.ports.DraftNotFound`.

A write token grants write. `component.write_token_sha256` and `composition.write_token_sha256` hold the SHA-256 digest of each draft's token, written by the create that inserts the row and never updated. `write_token_digest()` returns the digest, or `None` for a row created before migration 0007, and `assembler.pipeline.write_component` compares it with the token the caller sent. The store checks no caller or session itself.

A component write token is also the idempotency key of the create that stored it. A unique index, `component_write_token_sha256_key`, holds one component per digest, and `component.create_request_sha256` holds the SHA-256 of the create request, passed to `begin_write` as `create_request_sha256`. `prior_create(write_token_sha256=...)` returns `assembler.ports.PriorCreate` (`component_id`, `composition_id`, `create_request_sha256`) for the component holding a digest, or `None`, reading in its own transaction so it sees every committed create.

## Relational Schema and Migrations

Database tables reside in the `presentation` schema. Migrations run through `dataset_store.migrate.apply_pending`, tracking applied versions in `presentation.presentation_store_schema_migrations`.

### Schema Tables

| Table                               | Primary Key                  | Description                                                                                                                                               |
| ----------------------------------- | ---------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `presentation.composition`          | `composition_id`             | Container tracking composition identity, creation timestamp, and the nullable `write_token_sha256` digest.                                                |
| `presentation.composition_revision` | `(composition_id, revision)` | Append-only revision log. Stores `blocks` JSONB (ordered array of `{"component_id", "revision"}`) and `actor`.                                            |
| `presentation.component`            | `component_id`               | Component registry row. Holds optional `composition_id` foreign key assigned at creation, the nullable unique `write_token_sha256` digest, and the nullable `create_request_sha256` digest. |
| `presentation.component_revision`   | `(component_id, revision)`   | Append-only component state. Stores `stored_intent` JSONB, `resolved_payload` JSONB, `series_coordinates` JSONB, `catalog_version`, `schema_version`, the minting release's `formatter_profile` JSONB, and the nullable `frame_rendering` JSONB of the frame the revision draws. |

### Migration Sequence

- `0001_bootstrap.sql`: Creates schema `presentation` and grants default privileges to `{{RUNTIME_DB_USER}}`.
- `0002_composition.sql`: Creates `composition` and `composition_revision` tables.
- `0003_component.sql`: Creates `component` and `component_revision` tables with foreign keys to `composition`.
- `0004_draft_lease.sql`: Creates the `draft_lease` table and its index on `expires_at`. `0009` drops them.
- `0005_series_coordinates.sql`: Adds nullable `series_coordinates` JSONB column to `component_revision`.
- `0006_bar_chart_axes.sql`: Renames a stored bar_chart component's `x_axis`/`y_axis` keys to `category_axis`/`value_axis`.
- `0007_write_token.sql`: Adds nullable `write_token_sha256` bytea columns to `component` and `composition`. Rows created earlier keep NULL and refuse every write.
- `0008_idempotent_create.sql`: Adds the partial unique index `component_write_token_sha256_key` on non-NULL `component.write_token_sha256` and the nullable `create_request_sha256` bytea column on `component`.
- `0009_drop_draft_lease.sql`: Drops the `draft_lease` table and its index.
- `0010_revision_formatter_profile.sql`: Adds the `formatter_profile` JSONB column to `component_revision`, fills it with the 2026.8.0 profile on rows stamped `2026.8.0`, and makes it NOT NULL with that profile as its default. Any row stamped with another release fails the migration.
- `0011_revision_frame_rendering.sql`: Adds the nullable `frame_rendering` JSONB column to `component_revision`, with no backfill.

### Running Migrations

Migrations execute with CLI migrator credentials:

```bash
python -m presentation_store.migrate up
```

Environment variables:

- `PRESENTATION_STORE_MIGRATOR_DB_USER`
- `PRESENTATION_STORE_MIGRATOR_DB_PASSWORD`
- `PRESENTATION_STORE_RUNTIME_DB_USER`

## Store Operations

### Transaction Lifecycle and Write Discipline

`LivePresentationStore.begin_write` coordinates a single-transaction context manager (`_LiveWriteContext`):

```python
with store.begin_write(
    component_id=component_id,
    is_create=True,
    composition_id="new",
) as ctx:
    ctx.append(record=revision_record, composition_entry=composition_append)
```

Write operations follow a set sequence:

1. `allocate_component_id()` mints component IDs before opening the transaction, so a card's description can name its component.
2. Lock acquisition follows a strict hierarchy: composition rows first, then component rows. When modifying an existing composition, a `SELECT ... FOR UPDATE` locks the composition row.
3. A `composition_id` other than `"new"` that names no composition, or a revise of a component id that names no component, raises `assembler.ports.DraftNotFound`.
4. A create whose `write_token_sha256` another component already stores raises `assembler.ports.WriteTokenInUse`, and the transaction rolls back, including any composition it minted. When the other create has inserted but not committed, Postgres holds this insert until that transaction ends: a commit raises `WriteTokenInUse` here, a rollback lets this create proceed. The store tells the two apart by the constraint name pg8000 reports with `SQLSTATE 23505`.
5. Any other duplicate freshly generated component or composition ID (`SQLSTATE 23505`) raises `GeneratedIdCollision`. Retrying creates a new ID.
6. Inserting into `component_revision` enforces uniqueness on `(component_id, revision)`. Duplicate key violations (`SQLSTATE 23505`) map to `assembler.ports.EditConflict`.
7. When attaching to a composition, the store updates `blocks` for existing components or appends new entries to `presentation.composition_revision`.

### Frame Store Operations

`LiveFrameStore` coordinates frame reads and artifact retention across services.

`load(frame_ref)`:

1. Validates the version, its revocation and its base version's, and servability in one `dataset_store.snapshot.read_servable_version` transaction, the check the snapshot door makes.
2. Retrieves raw frame bytes from `ArtifactStore`, caching results in memory up to 64 MB.
3. Computes the `StructuralView` with `assembler.frame_view.compute_structural_view`.
4. Resolves display labels for `stat_var`, `entity`, and `provenance` IDs through `GraphReader.node_arcs_many`, capped at 300 references per call.
5. States the frame's rendering as `ResolvedFrame.rendering`: a dataset frame's from its version record and linked files on every load, a derived frame's recipe `normal_form_hash`. A write stores it on the revision as `frame_rendering`.

`pin(frame_ref, component_id)`:

1. Promotes the canonical artifact from `working` to `pinned` tier in `ArtifactStore` when currently in the working tier.
2. Inserts an artifact reference record (`reference_kind="presentation_draft"`, `principal="presentation:<component_id>"`) into `datasets.artifact_reference` using `ArtifactReferenceWriter`.
3. For a derived (`ops_`) frame, pins each root version its recipe names (each root's `dataset`), and theirs in turn. A derived frame with no recipe yet pins alone; a store with no recipe reader, or a root naming no dataset version, refuses `frame_unavailable`.

No create, revise, or render pins. `pin_card_frames(component_id, revision, revision_store, frame_store)` pins the frame a card revision draws, and a share calls it for each card it first includes.

`release_pin(frame_ref, component_id)`:
Removes the `presentation_draft` reference via `ArtifactReferenceWriter.remove_reference`. Cleanup tasks use it after confirming that the referenced component is absent.

### Reclaim Inspection

`LivePresentationStore` provides an inspection query for cleanup tasks:

- `list_orphaned_presentation_references(referenced_component_ids)`: Finds `presentation_draft` artifact references whose `component_id` is missing from `presentation.component`.

## Connection Lifecycle and Environment Configuration

`presentation_store.connection.PresentationStoreSettings` defines connection parameters, and `presentation_store.provider` manages pooling.

Connections support the Cloud SQL Python Connector with Google Cloud IAM database authentication, or direct TCP connections.

`provider.shared_pool()` maintains a process-wide, reference-counted `ConnectionPool`. Borrowers obtain connections from the pool and return them through `provider.close_shared_pool()`. Resources close once all active borrowers release the pool.

### Environment Variables

| Variable                                      | Default        | Purpose                                                           |
| --------------------------------------------- | -------------- | ----------------------------------------------------------------- |
| `PRESENTATION_STORE_INSTANCE_CONNECTION_NAME` | `None`         | Cloud SQL instance connection string (`project:region:instance`). |
| `PRESENTATION_STORE_HOST`                     | `127.0.0.1`    | Database server hostname for TCP connections.                     |
| `PRESENTATION_STORE_PORT`                     | `5432`         | Database server port.                                             |
| `PRESENTATION_STORE_DATABASE`                 | `presentation` | Target database name.                                             |
| `PRESENTATION_STORE_RUNTIME_DB_USER`          | _Required_     | Database user for runtime operations (IAM or standard).           |
| `PRESENTATION_STORE_RUNTIME_DB_PASSWORD`      | `None`         | Database password for runtime TCP connections.                    |
| `PRESENTATION_STORE_POOL_SIZE`                | `2`            | Connection pool size.                                             |
| `PRESENTATION_STORE_CONNECT_TIMEOUT`          | `30.0`         | Connection timeout in seconds.                                    |

## Error Hierarchy

Store operations map driver and infrastructure exceptions into structured domain types:

```
Exception
├── PresentationStoreError (Base)
│   └── PresentationStoreConfigError      # Configuration parsing and environment errors
├── GeneratedIdCollision                  # Retryable fresh component/composition ID collision
└── PresentationStoreUnavailable          # Database or connection failures during transactions
```

`PresentationStoreUnavailable` formats messages using `safe_diagnostics(exc)`, logging only the qualified exception class and PostgreSQL SQLSTATE code. Error messages omit query text and parameter values. It carries the failing driver exception's own SQLSTATE code as `sqlstate` (`None` for a failure with no SQLSTATE at all). `presentation_api.doors.components.classify_components_exception` splits on `dfo_platform.store_errors.store_failure_is_permanent(sqlstate)`: a permanent class (malformed statement, violated constraint, unsupported feature) maps to `internal_error`, HTTP 500, not retryable; every other class, including `None`, maps to `service_unavailable`, HTTP 503, retryable. It also carries `connection_broken`, true when `dataset_store.connection.default_is_broken` judged the driver failure a dead connection; the shared pool's `store_errors.is_broken` reads it and closes that connection.

`GeneratedIdCollision` applies when a generated component or composition primary key collides. The components door maps it to retryable `service_unavailable`. Other integrity violations remain `PresentationStoreUnavailable` and non-retryable.

Domain mappings translate PostgreSQL errors into `assembler.ports` exceptions:

- `DraftNotFound`: No component or composition exists at the requested id.
- `WriteTokenInUse`: A create's component write-token digest collided on `component_write_token_sha256_key` (`SQLSTATE 23505`). `prior_create` names the component that holds it.
- `EditConflict`: Duplicate revision insert (`SQLSTATE 23505`), or a revised component whose stored composition row is missing.
- `GeneratedIdCollision`: A newly minted component or composition ID collided (`SQLSTATE 23505`). Retrying allocates another ID.
- `FrameUnavailable`: Frame is revoked, missing, expired from working tier, or unreachable due to storage errors.

## Test Doubles

Unit tests use domain doubles defined in `tests/presentation_store/conftest.py`:

- `FakePresentationStore` and `FakeTransaction`: In-memory doubles implementing the SQL access patterns of `LivePresentationStore`.
- `FakePresentationState`: Provides state snapshot and rollback methods to test transaction aborts and failure isolation.
- `Clock`: `LiveFrameStore` accepts an injectable `Callable[[], datetime]` to test artifact servability deterministically.
